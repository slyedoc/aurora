aurora frame pipeline

Remove the ~1.7 ms GPU-idle bubble per frame, put all GPU sync on one timeline semaphore, add Reflex and present timing, record in parallel, and move binding to VK_EXT_descriptor_heap. Written 2026-10-13. Implementation notes: frame-pipeline-notes.md.

Status 2026-10-13: phases 0–3 done (aurora b5c101e and the cleanup after it); results, deviations and what is deferred are in the notes.

Why. Measured in Northshire (Tracy, 4,109 frames): frame period 7.41 ms, CPU waits on the frame fence 0.02 ms, then records for a median 1.74 ms (p90 2.41) before the next submit. With one frame in flight the GPU has nothing queued during that time: it is idle at least 23 % of every frame while "GPU-bound".

The rule this plan keeps. No CPU-visible readback gets older than today. One frame stays in flight; the CPU waits for frame N before it consumes anything frame N produced (transform rows, exposure, pick hits, timestamps, screenshots). What moves is recording, which needs handles, not results. This is the line the old aurora-rt-pipeline branch crossed (camera on a rig, one-frame-late world poses) and this plan does not.

Decisions you are most likely to tweak

D1. The new order of Last (frame model)

today:   Extract → Fence(wait N) → Prepare → Render(record + host writes) → Submit
planned: Extract → Prepare → Record(N+1, parity p) → Fence(wait N) → Latch → Submit(N+1)
  • Prepare / Record may only write memory the GPU is not reading: the parity-p half of a per-frame buffer, a vkCmdUpdateBuffer (copied into the command buffer at record time, applied in GPU order), or a fresh staging slice.
  • Latch runs after the wait: anything computed from frame N's readbacks (RR input exposure from the exposure readback, pick hits) is written there into small single-copy host buffers. Frame N is done, so single copies are safe.
  • Systems not converted yet stay after the wait, as today. Conversion is per subsystem and can land in any order: a half-done tree is correct, just not yet fast.

Alternative considered: host-signalled timeline (submit early, vkSignalSemaphore after latching). Not needed once the latch is just readback-derived values; kept as a later option if Latch ever grows.

D2. One timeline semaphore replaces every fence (new type)

pub struct GpuTimeline { semaphore: vk::Semaphore /* TIMELINE */, next: u64 }
#[derive(Copy, Clone, PartialEq, Eq, PartialOrd, Ord)] pub struct SubmitPoint(u64);

impl GpuTimeline {
    /// Queue `cmds` after `waits` (binary swapchain/XR semaphores keep their stage), signal and
    /// return the next point. Caller holds the queue (until D7 makes that unnecessary).
    pub fn submit(&mut self, queue, cmds: &[vk::CommandBuffer], waits, binary_signals) -> SubmitPoint;
    pub fn wait(&self, point: SubmitPoint);          // vkWaitSemaphores
    pub fn reached(&self, point: SubmitPoint) -> bool; // vkGetSemaphoreCounterValue
}
  • Replaces: the frame fence (FrameSync), the transform readback fence, the picker fence and its binary semaphore, the per-call transfer fences in run_transfer_commands. Screenshot/video readbacks already ride the frame fence; they keep doing so through the frame's point.
  • Swapchain acquire / present stay binary (the swap chain requires it), but get one acquire semaphore per parity (today one is shared by all frames).
  • Vulkan's vkQueueSubmit2 with VkSemaphoreSubmitInfo is used throughout (synchronization2 is core in 1.3).
  • The destroyer keeps its two-tick deferral (an object enqueued while recording N+1 dies after N+1's own wait). Optionally later: key destruction on SubmitPoint instead of ticks.

The SBT is rewritten in full every frame because skinned hit records flip parity. Two options: Parity<SBT> (simple, 2× size) or move the flip into the hit shader (read vertex_buffer[frame & 1]) so the SBT changes only with the scene. Plan: Parity first, shader flip later (it also removes the 0.21 ms update_sbt).

D4. What becomes user-facing (settings / F3)

  • F3 "Frame" graph: GPU busy, GPU idle (gap between one frame's last timestamp and the next frame's first), CPU record time, latch time, present-to-display latency (D5). Also Tracy plots gpu idle ms, cpu record ms.
  • Bench: new scopes idle and record next to busy/trace/dlss (benches/northshire.rs in zero).
  • RenderSettings::low_latency: Off | On | Boost (Reflex). Default On where VK_NV_low_latency2 exists, Off elsewhere. Not in XR (the OpenXR runtime paces).
  • No new env vars; everything on RenderSettings and the F3 panel.

D5. Reflex and present timing (phase 1.5)

  • Swapchain created with VkSwapchainLatencyCreateInfoNV; per frame vkSetLatencyMarkerNV: SIMULATION_START (First), SIMULATION_END (end of PostUpdate), RENDERSUBMIT_START/END (around Record→Submit), PRESENT_START/END; vkLatencySleepNV at the top of First — the CPU is held there, not in the fence wait.
  • Present timing via VK_KHR_present_wait2 (present ids, measured display latency for F3) and VK_EXT_swapchain_maintenance1 present fences so swapchain resources (acquire semaphores, old swapchains on resize) are released by fact, not by queue_wait_idle.
  • Reflex sleep vs. vsync/FIFO: with FIFO the driver already throttles; Reflex mostly matters for uncapped/VRR. Default proposal: On regardless (it is cheap); revisit if pacing looks worse.

D6. Parallel recording (phase 2)

  • Each recording system gets its own command pool per worker thread (ThreadLocalPools, reset at the frame's start) and records one primary command buffer; a final submit_frame system submits them in a fixed order in one vkQueueSubmit2. GPU order = submit order, so CPU recording order is free.
  • Proposed split (Bevy runs them in parallel where access is disjoint):
    scene (frame commands → skins → TLAS → lights/SHaRC; one chain, it is ordered by data) ‖ exposure+atmosphere ‖ per-view trace+DLSS (both XR eyes in parallel) ‖ UI surfaces ‖ present pass (post, gizmos, UI).
  • NGX (DLSS evaluate) thread safety across views is not documented as safe: proposal is to record the trace per view in parallel but call evaluate for all views from one system, serially, into their own command buffers.

D7. Queue access

  • Enable VK_KHR_internally_synchronized_queues when present: create the queue with INTERNALLY_SYNCHRONIZED and drop rd.queue.lock() on that path. Without it, keep the mutex.
  • The XR runtime and NGX submit on the same queue internally. WiVRn/OpenXR still get the mutex around their calls (they do not know the queue is internally synchronized); keep run_transfer_commands_exclusive for NGX feature creation.

D8. Descriptor heaps (phase 3) (binding model)

  • One resource heap and one sampler heap (vkCmdBindResourceHeapEXT/SamplerHeap), descriptors written with vkWriteResourceDescriptorsEXT into a host-visible heap buffer. Replaces the bindless set (16,536 textures, binding 200), the RT sets (TLAS + 8 guides), the post sets (10 images), the gizmo sets.
  • Per-frame descriptors (guides, swapchain views, TLAS) live in a Parity region of the heap; textures in a persistent region. Shaders get indices through push data (vkCmdPushDataEXT) or the existing push constants.
  • Slang: compile with the spvDescriptorHeapEXT capability; bindless handles (DescriptorHandle<T>) become heap accesses. All [[vk::binding]] globals in raygen/quad/gizmo/ui shaders change.
  • Fallback when the extension is missing (AMD iGPU here, older NVIDIA drivers): require it (clear startup error naming driver 610+) vs. keep descriptor sets as a second path. Proposal: require it — two binding models double every shader's binding code, and both target machines are NVIDIA.
  • Revision 1 extension; Khronos plans a KHR version, so expect a follow-up port. Validation-layer coverage in SDK 1.4.350 to be checked first.
