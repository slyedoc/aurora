Async compute

aurora, 2026-10-15. In-frame overlap only: one frame on the GPU at a time, as now. Cross-frame pipelining is out of scope.

Why. GPU Trace of Northshire (3840x1080, Balanced, aurora a62fe19): the frame averages 26 % SM throughput and 21 warps per SM. The scene lane (frame commands 0.225, skins 0.236, tlas 0.135 ms) runs at 0.4-7 % SM; skins is the skinned BLAS refits, fixed-function work with 0.9 warps/SM. The primary pass and the trace hold 18 warps/SM (126-register raygens). Everything is serial on one queue. Work that does not depend on what runs beside it can fill those SMs from a second, compute-only queue (family 2: 8 queues, 64-bit timestamps).

Decisions

D1. A compute-only queue; buffers and images shared CONCURRENT

One queue from the compute-only family (2 on NVIDIA). Every buffer and storage/sampled image is created CONCURRENT over the graphics and compute families (one place each: create_buffer, vk_init::image_info), so no ownership transfers are needed; NVIDIA has no cost for concurrent sharing. The swapchain stays EXCLUSIVE (graphics only). Without a compute-only family everything stays on the one queue, in the same order.

Alternative: EXCLUSIVE with release/acquire barriers per crossing. More barriers and more to get wrong; no gain on NVIDIA.

D2. The existing timeline stays the retirement clock

Today one timeline orders everything, and "point N reached" means every earlier submit finished; the destroyer, GPU retire and bindless slot reuse rely on it. That stays true if every frame's last graphics submit waits on the frame's last compute submit: reaching a graphics point then implies the compute work before it finished too. A second timeline semaphore orders the compute submits within a frame (graphics waits on it, compute waits on graphics points). Nothing that retires resources changes.

Alternative: a timeline per queue and retirement over both. More general (compute work could outlive a frame), but every retirement site changes; not needed while compute work never ends a frame.

D3. The frame as three graphics submits and two compute submits

graphics queuecompute queue
G1 uniform/environment upload, frame commands (scatter)C1 waits G1's upload: skins + skinned BLAS refits, exposure, atmosphere LUTs, SHaRC resolve, fog reproject
G2 waits C1: TLAS, lights, fog grid (RT light, soften, integrate), primaryC2 waits G2's lights: ReSTIR grid (overlaps the fog grid and the primary pass)
G3 waits C2: ReSTIR temporal + spatial, trace, DLSS, post prep, present

Semaphore waits at the exact stage that reads (not ALL_COMMANDS). The groups are a first cut from the code; phase 1 audits every read and write before anything moves, and a pass whose inputs turn out to cross a boundary stays where it is.

D4. The bench measures the frame's span, not the sum of its scopes

busy sums the scopes, which counts overlapped work twice. With two queues the measure is span: first to last timestamp across both queues (one device clock). The profiler gets a query pool on the compute queue. A/B on span and the trace's own scope.

D5. NGX, XR and present stay on the graphics queue

DLSS evaluate, the XR compositor's submits and the swapchain present are untouched.

Expected

Overlappable under the scene lane: skins + BLAS 0.24, exposure + atmosphere 0.04, SHaRC resolve 0.05, fog reproject ~0.02 ms. Under the primary pass: ReSTIR grid 0.06 ms. Ceiling about 0.35-0.4 ms of a 5.5 ms frame; realistic 0.2-0.3, less what the extra submits and semaphores cost.

Phases

  1. Measure. Bench and profiler report span; baseline taken.
  2. Plumbing, nothing moved. Compute queue and command pools, the compute timeline, CONCURRENT sharing, profiler queries on the compute queue, the frame split into its submits with everything still on graphics. Shots identical; span unchanged within noise. Validation clean.
  3. C1. Dependency audit of the scene-lane group, then move it. A/B span; shots; XR.
  4. C2. ReSTIR grid under the primary pass.
  5. Barrier audit. Narrow the ALL_COMMANDS barriers that serialise same-queue work, now that the timeline shows what waits on what.

Mechanical notes

  • render_device.rs: pick the compute family, create the queue (internally synchronized like the main one), a command pool and per-parity command buffers for it.
  • timeline.rs: a compute timeline beside the main one; submits take waits on either (value + stage mask).
  • render_buffer.rs / render targets: queue family indices on creation (CONCURRENT).
  • gpu_profiler.rs: a second query pool; scopes tagged by queue; span across both.
  • ray_render_plugin.rs: lanes record into the submit they belong to; submits in order G1, C1, G2, C2, G3 with their waits.
  • Test: Northshire bench A/B on span, shots, 90 s validation, XR (two views), a skinned character on screen.
